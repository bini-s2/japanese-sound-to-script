# Chat continuation & execution workflow

이 문서는 Japanese Sound to Script를 ChatGPT와 함께 반복 수정할 때의 **대화 방식, 실행 방식, 검증 방식, 인수인계 방식**을 정리한다.

목표는 새 채팅에서도 “지난 방에서 어떻게 일했는지”를 다시 설명하지 않고 곧바로 작업하는 것이다.

---

## 1. 기본 협업 모드

이 프로젝트의 대화는 “아이디어 상담 → 사용자가 직접 구현” 방식보다 **사용자 피드백 → ChatGPT가 실제 GitHub 수정 → Vercel 배포 확인 → 링크 전달** 방식으로 진행한다.

사용자가 보통 하는 요청:

- 스크린샷에서 이상한 검색 결과를 지적
- 특정 발음/문장 검색이 안 된다고 보고
- UI 버튼/카드/텍스트의 세부 스타일 수정
- 후보 정렬이나 의미/발음 표시 방식 변경
- 새 검색 규칙 추가
- `/log`로 작업 기록

이때 단순 설명으로 끝내지 말고 가능한 경우 바로 수정한다.

## 3. 한 요청을 처리하는 표준 루프

### A. 요청 이해

스크린샷 또는 사용자의 예시 입력에서 아래를 구분한다.

- Data coverage 문제
- 검색 exact/fuzzy 문제
- 발음 변환 문제
- 띄어쓰기/구문 분절 문제
- 후보 랭킹 문제
- 의미 번역 문제
- UI hierarchy / styling 문제

### B. 최신 소스 확인

변경 전 반드시 대상 파일을 fetch하여 현재 blob SHA를 확보한다.

같은 파일을 연속 수정할 때 이전 SHA를 재사용하지 않는다.

### C. 수정

원칙:

- 관련된 부분만 변경
- 사용자 요청에 없는 디자인 리뉴얼 금지
- 오류 한 건을 위한 임시 하드코딩보다 재사용 가능한 규칙 우선
- 단, 일반화 때문에 정상 검색이 망가지지 않도록 후보 품질 필터와 threshold를 함께 조정

### D. 검증

최소한 다음을 확인한다.

- 변경 파일이 GitHub에 정상 반영됨
- Vercel status가 `success`
- 기존 핵심 예제가 깨지지 않을 가능성이 높은지
- 새로운 예시가 검색 UX 원칙과 맞는지

### E. 사용자 회신

최종 회신은 길지 않게:

1. “고쳤어”
2. 핵심 수정 2~5개
3. “Vercel 재배포 성공 확인”
4. https://sound-to-script.vercel.app/
5. 테스트 입력 몇 개

## 4. 검색 문제를 고치는 방식

### 정확히 일치하는 단어가 적은 문제

사전 커버리지를 넓히되, 단순히 결과 수를 늘리는 것이 목표가 아니다.

**좋은 결과가 위에 오는 것**이 더 중요하다.

### 입력이 부정확한 경우

사용자가 다음처럼 입력할 수 있다고 전제한다.

- 장음 누락
- 촉음 누락
- 자음 혼동
- 한글 표기 흔들림
- 띄어쓰기 누락
- 조사/동사 경계 누락
- 한글로 들린 일본어 + 영어/외래어 혼합
- 가사/대사 한 문장 전체

결과는 가능한 경우 아래 형태로 안내한다.

- 가장 유사
- 발음 보정
- 의도 추정
- 혹시 이 표현을 찾으셨나요?

### 후보 랭킹

가장 가까운 후보가 **항상 위**에 있어야 한다.

단순 prefix match 때문에 훨씬 긴 단어가 위로 뜨지 않게 한다.

### 문장/구 검색

띄어쓰기가 없어도 일본어의 단어 + 조사 + 동사 구조를 먼저 고려한다.

예:

`도코에이코`

→ `도코 + 에 + 이코`

→ `どこ + へ + 行こう`

→ `どこへ行こう`

→ “어디로 갈까? / 어디에 갈까?”

### 이상한 후보 차단

다음 결과는 높은 확신도로 노출하지 않는다.

- 의미 없는 한자/가나 혼합
- 번역기/IME가 억지로 만든 문자열
- 작품명/고유명사만 일치하는 결과
- 입력보다 지나치게 긴 항목
- 발음 유사도가 낮은 후보

## 5. 뜻과 발음 표현

결과 화면의 권장 정보 순서:

1. 일본어 원문
2. 일본어 읽기
3. 한국어식 발음
4. 자연스러운 한국어 뜻
5. 필요할 때 상세 설명

예:

`東京フラッシュ`

`とうきょうフラッシュ`

발음 · `도쿄 후랏슈`

뜻 · `도쿄 플래시`

사전의 “노래 제목”, “작품명” 같은 메타 텍스트를 뜻처럼 그대로 보여주지 않는다. 일반 사용자가 이해할 수 있는 **표현 자체의 자연스러운 의미**를 우선한다.

---

## 6. UI 수정 원칙

- 요청받은 부분 외에 임의 수정 금지
- 버튼 외 요소: fill과 border를 동시에 쓰지 않는다
- 일본어 원문이 가장 크게
- 읽기/발음은 보조 계층
- 뜻은 명확하게
- 유사 후보는 리스트형으로 빠르게 비교 가능하게
- 너무 많은 카드/대시보드 느낌을 피한다
- 버튼 상태는 Primary / Outline 등 계층이 분명해야 한다

---

## 7. 대화 톤

- 한국어
- 짧고 친근하게
- 실제 수정이 끝났으면 결과부터 말한다
- 가끔 `ㅋㅋㅋ`, `ㅠㅠ`, 💙 정도의 가벼운 표현은 자연스럽게 사용 가능
- 기술 설명은 사용자가 이유를 물을 때 더 자세히
- 사용자의 버그 리포트가 맞다면 바로 인정하고 원인을 설명한다

피해야 할 답변:

- 이미 연결된 GitHub 작업에 대해 “직접 수정할 수 없다”
- 수정하지 않았는데 수정했다고 말하기
- Vercel 확인 전 “배포 완료”
- 매번 같은 프로젝트 설명을 사용자에게 다시 요구하기

기능:
- `feat: ...`

- `fix: ...`

- `ui: ...`

- `build: ...`

로그:
- `log: ...`

## 10. 현재 검색 QA용 회귀 테스트 세트

검색 로직을 크게 바꾼 뒤에는 아래와 비슷한 케이스를 함께 확인한다.

### 기본 단어

- `와타시`
- `아리가토`
- `다이죠부`
- `스고이`
- `와카라나이`

### 조사/짧은 구

- `키미노` → `君の`
- `보쿠와`
- `키미가`

### 띄어쓰기 없음

- `도코에이코` → `どこへ行こう`
- `키미가스키`
- `와타시와다이죠부`

### 장음/발음 보정

- `히토츠데이` → `ひとつでいい` 가능성
- 촉음이 들어가는 가타카나 표현
- 유사 자음이 섞인 입력

### 문장

- `아지가 시나인다`처럼 한글로 기억한 문장

### 외래어 혼합

- `도쿄플래쉬` → `東京フラッシュ`

이 세트는 “정답 DB”가 아니라 회귀 테스트용 대표 입력이다. 검색 로직을 바꿀 때 이전보다 더 이상해진 항목이 없는지 확인한다.

## 11. /log 자동 동작

사용자가 `/log`라고 보내면:

1. 현재 작업 중 의미 있는 완료 사항만 요약
2. `bini-s2/Design-log`의 해당 날짜 경로에 기록
3. 공개 저장소에 올려도 괜찮은 기술/디자인 정보만 포함
4. commit SHA를 사용자에게 알림

질문으로 다시 확인하지 않는다.

1. `bini-s2/japanese-sound-to-script/AGENTS.md`
